# Kiro 流式首字延时与工具参数输出改造方案

日期：2026-11-05

状态：第一批（分段计时）已于 2026-11-05 实施。第二批的可选 `KIRO_TOOL_STREAM_MODE=incremental` 已于 2026-11-13 实施并使用本地开放模拟上游验证首段真实参数在 stop/EOF 前输出；默认仍为 validated。原生工具、快照冲突、交错调度、预算、取消及入口隔离的回归见 `tests/kiro-tool-incremental.test.js`。本地测试不代表线上灰度验收；尚未通过真实 CLIProxyAPI 链路做参数增量对照，也未采集完整上游首参配对基线。配置、失败语义与客户端执行前提见 [Kiro 生产保护与兼容性开关](KIRO_PRODUCTION_SAFETY.md)。下文“拟议”部分保留设计背景，实施与线上验收状态以本段为准。

## 目标与范围

本次改造优先解决工具参数在服务内等待收齐后才输出的问题，并补齐分段耗时统计，区分上游等待、本地处理和下游发送。模型的思考时间、参数生成时间与请求总用时分别评估，不用响应头、心跳或空的协议开始事件代替真实首字。

实施范围包括 Kiro 工具参数组装、流式内容块调度、跨协议转换验证、分段计时、配置开关和回归测试。第一阶段优化原生工具事件；文本形式的 `[Called ... with args: {...}]` 继续完整解析与校验。

工具参数提前传输可改善参数展示和生成进度，工具实际执行仍需等待完整参数。该改造不承诺缩短模型生成本身的时间，也不能直接消除上游数秒后才开始返回内容的等待。

不在本次主改动中统一降低 effort、自动判断任务复杂度、裁剪历史或重写 Rust/Go 传输层。后续调整须由分段计时和对照结果支持。

## 已确认的现象与证据边界

### 线上日志

- 部分 Opus 请求从上游思考事件到下游发送仅间隔 0–1 毫秒，不能把所有慢请求归因于整段响应缓冲。
- 一次工具请求的首个上游工具事件在请求开始后 3559 毫秒到达，首个下游事件在 4885 毫秒发送，中间相隔约 1326 毫秒。工具开始事件不等于首段非空参数，需要新增指标进一步区分。该间隔从只带工具名的事件算起，是这次请求改为增量输出后可节省时间的上限；目前只有这一个样本。
- 样本中 Opus 等待上游响应头约 3185–7003 毫秒。现有计时合并了本地中继、代理、网络和上游等待，尚不能直接归责到某一组件。
- 三次 Sonnet 请求明确使用 `stream: false`，其完整响应到达时间与请求结束时间接近符合非流式行为。
- 原始长上下文请求的部分输入 token 数来自 `contextUsagePercentage` 推算，不能当作权威 usage。
- 样本请求走普通 `/v1/messages` 路径，现有证据不支持把 `KIRO_CC_BUFFERED=true` 作为该样本的主要原因。

### 本地基线

现有基线记录：2026-11-05 对当时的 9 个测试文件执行 `--runTestsByPath`，共 286 项通过；本方案后续补充的回归测试不包含在该次统计内。使用每段相隔约 100 毫秒的四段模拟输入时，普通文本约 103 毫秒出现首段、约 405 毫秒结束；整段缓冲文本约 402 毫秒才出现首段；当前工具流约 403 毫秒才出现首段参数、约 404 毫秒结束。

### Kiro IDE 的处理方式

依据：静态阅读本机 Kiro IDE 1.4.62（kiro-agent 扩展 1.1.641）的 `extension.js` 和本机日志，未抓包。

- 每个 `toolUseEvent` 片段到达后立即作为 `tool_call_chunk` 交给界面，参数是未拼完的原始字符串；首个片段带 ID 和名称，`stop` 标记参数结束。这与本文 incremental 模式的事件顺序一致。
- 流事件解析只接受字符串形式的 `input`，非字符串直接丢弃，IDE 自身不做完整对象替换。这只说明 IDE 的处理方式，不能证明上游从不发送对象形式的参数，第一批仍需统计快照。
- CreateResponse 路径把每个 `response.function_call_arguments.delta` 转成一个参数片段，说明该接口按片段返回参数。本项目使用的旧端点 `q.us-east-1.amazonaws.com` 在大参数时是否同样分段返回尚未验证，由第一批的大参数探测确认。
- IDE 的首字计时在首个正文、思考或工具事件到达时触发，工具事件包括只带名称、参数为空的事件。这与第 7 节的口径不同，两边数字不能直接比较。
- 本机日志中 IDE 的 Opus 5.5 请求走 CreateResponse（`runtime.us-east-1.kiro.dev`），与本项目的端点不同。

## 设计方案

### 1. 将增量通知与最终校验分开

保留组装器现有 `feed()` / `finish()` 兼容入口，新增增量更新入口，例如 `feedUpdates()` / `finishUpdates()`。接口名可在实施时调整，但两组接口必须共用内部状态机，同一事件不能重复送入两组入口。

内部更新区分工具身份确认、参数追加、完整对象快照和校验完成。调用使用稳定的内部标识关联状态，避免临时上游 ID 迁移后错配已排队片段。

组装器继续保留完整参数以完成最终校验；输出层跟踪已发送位置，只发送新增片段，避免每次重新发送整个累计字符串。参数累计字节数、调用数量、跨片段 UTF-16 代理对计数继续沿用现有保护。

最终校验仍要求参数为合法 JSON 对象。明确结束的无参数调用可以输出 `{}`；未结束的空调用、损坏 JSON、孤立或含糊片段不能修复成成功调用。正常 EOF 补全有效参数的现有兼容规则保留，帧完整性和可选的严格结束原因检查也继续生效。

### 2. 按收到的片段发送参数

拟新增 `src/providers/claude/kiro-tool-stream.js`，集中处理输出调度，避免把所有状态继续堆入主生成函数。

正常调用的事件顺序：

```text
确认真实工具 ID、名称，并收到首段非空参数
  → 输出此前待发的文本或思考，关闭对应内容块
  → content_block_start(type=tool_use, input={})
  → content_block_delta(type=input_json_delta, partial_json=首段参数)
  → 后续参数片段逐段发送
  → 工具结束或符合兼容规则的正常 EOF
  → 完整 JSON 校验通过
  → content_block_stop
  → 所有块、元数据和完整性检查完成
  → message_delta 与 message_stop
```

只有校验完成的调用才进入最终 `toolCalls`，参与用量统计、最终结束原因和成功结果。首段发送不能等待完整 JSON，但也不能只凭工具名提前输出空的工具开始事件来改善首字指标。

Anthropic 原生流式接口和 Kiro IDE 都在确认工具名称后先发开始事件，再逐段发送参数。本方案等到首段非空参数才发开始事件，是有意的取舍：更早发送会让 `anyDataSent` 更早为真，缩短第 5 节所述的透明重试窗口。若日后改为确认身份后即发送开始事件，首字指标仍不计入该事件。

保留 `generateContentStream()` 对初始 `message_start` 的暂存与空响应重试保护。增量路径只有具备可发送的真实内容时才释放开始事件。

### 3. 明确完整对象替换的行为

现有组装器仅在完整对象具有至少一个自有可枚举字段时，用它替换之前收到的字符串片段；空对象 `{}` 不覆盖已有参数。增量通知、快照统计和冲突判断都应沿用这一条件。已发送字节不能撤回，因此增量模式与完整替换兼容性之间存在实际取舍。

| 状态 | 处理方式 |
| --- | --- |
| 收到空对象 `{}`，已有字符串参数 | 作为无操作保留原参数，不生成替换更新、不做快照前缀比较，也不计入快照冲突分母；同一事件的 stop 仍正常处理。 |
| 收到空对象 `{}`，尚无参数 | 暂不产生参数增量；明确 stop 时仍完成为合法的 `{}`，缺少结束且始终无参数时仍按现有规则失败。 |
| 收到非空完整对象，参数尚未发送 | 允许按现有语义替换，更新字节预算。 |
| 收到非空完整对象，已发送前缀与重新序列化结果完全一致 | 只发送尚未发送的后缀，继续校验和完成。 |
| 收到非空完整对象，与已发送前缀冲突 | 报明确的完整性错误并终止；不能回退缓冲并继续宣称成功。 |

前缀比较按实际字节对应的字符串内容处理，不能用语义相近的 JSON 替换已经发出的内容。需要保留任意完整对象替换能力的流量继续使用 `validated` 模式。

组装器收到符合替换条件的非空完整对象时用 `JSON.stringify(event.input)` 重新生成字符串。上游原始片段若带空格、key 顺序不同或使用 unicode 转义，即使语义相同也会判为冲突，可能把当前能成功的请求变成失败。第一批计时先统计“非空字符串片段之后又收到非空完整对象”的次数及前缀一致比例；空对象占位单独计数，不计入前缀一致或冲突比例。该比例属于灰度前的兼容性风险估计，实际冲突仍以增量模式已发送前缀为准；没有发送过参数的调用仍允许替换。冲突罕见时再进入灰度，冲突常见时先调整本节规则。

必须保留的兼容序列：先收到 `input: '{"path":"x"}'`，再收到 `input: {}, stop: true`，validated 与 incremental 最终参数都应为 `{"path":"x"}`，不能用 `{}` 覆盖或报快照冲突。

### 4. 保持身份、顺序与去重

- **真实 ID 晚到**：暂存只有名称或临时 ID 的调用，真实 ID 与名称确认后再开始增量输出。始终缺少真实 ID 的调用按现有兼容方式在完成后输出，不向客户端发送后又改 ID。
- **多个工具交错**：保持当前非重叠内容块约定。按块首次出现顺序调度；工具 A 已打开时，工具 B、正文和思考进入待发队列。继续读取上游，不能等待 A 完成而阻止读取完成 A 所需的后续帧。这会改变输出顺序：validated 模式下，A 未完成时到达的正文立即输出，排在 A 的块之前；incremental 模式下，A 打开后到达的正文排在 A 之后。
- **队列预算**：工具参数继续受现有参数预算限制；因块调度暂存的文本、思考和事件元数据增加明确的总量上限。重复保存的缓冲副本也需要纳入内存评估，超限明确失败，不能无限排队。
- **文本工具晚于原生工具**：暂存可能重复的文本工具，待对应原生调用校验完成并取得签名后再决定抑制或输出。
- **文本工具先输出**：本次响应后续调用使用完成后输出路径，在参数签名确定后去重，避免已输出文本工具与尚未完成的原生调用重复。
- **独立原生调用**：不同原生 ID 即使名称、参数相同，也保留为独立调用。
- **占位调用**：`no_tool_available` 及其关联片段继续过滤，不能解除首个有效事件期限或计入首字。

### 5. 保持失败、取消与计量语义

部分参数发出后发生参数错误、帧损坏、超限或上游中断时，发送客户端协议对应的流式错误并结束，不为失败工具补发正常 `content_block_stop` 或消息成功事件，不切换账号重放已输出内容。

完整性错误原因与恢复提示需要同时适配。`kiro-event-stream.js` 当前将 `No malformed tool call was emitted.` 追加到参数不完整错误中；已发送部分参数后不能沿用这一断言。组装层保留中立的错误原因，由统一出口根据失败调用的实际写入状态生成恢复提示：未向下游写入该工具片段时可以说明该调用尚未输出；已写入开始事件或参数时应说明“可能已发送部分工具调用，但失败调用未完成，不应执行或修补其参数”。两种状态都保留“不重放此前已完成调用、以实际工具结果判断执行状态”的约束，不声称整条响应中没有其他已完成调用。

写入状态以统一出口接受写入为准，不能仅因组装器产生了增量更新就认定客户端已收到。非流式内部消费事件也不代表已向客户端发送；写入状态未知时使用中立提示。新增参数快照冲突等错误同样遵守上述规则，并在现有客户端错误消息中表达，不擅自改变各协议的错误结构。

增量输出会缩小可透明重试的范围。纯工具响应（无思考、无正文）在参数收齐前出错时，当前 `generateContentStream()` 仍暂存 `message_start`，客户端尚未收到数据，外层空响应重试和账号切换仍可生效；incremental 发出首段参数后 `anyDataSent` 为真，同类错误直接以流式错误结束。实施前确认哪些错误类型当前依赖这条外层重试，灰度时单独统计“首段参数发出后失败”的次数。

部分参数发出后失败时，客户端会先收到不完整参数再收到错误事件。安全性依赖客户端只在 `content_block_stop`（或对应协议的完成事件）之后执行工具；未正确处理错误事件的客户端可能执行截断参数。灰度前确认目标客户端满足这一前提。

复用现有串行写入和背压机制。客户端断开或写入超时时，取消上游、关闭内部迭代器并释放并发插槽。新增待发队列随失败或取消一起释放。

完整性检查、用量汇总和缓存计量提交继续由原有成功边界控制；提前发送参数不能提前提交缓存账本或标记请求成功。

非流式请求与明确要求整段缓冲的请求继续使用完整校验路径，保留最终对象替换、输出结构和用量回填行为。

### 6. 配置与适用范围

拟新增配置：

```json
{
  "KIRO_TOOL_STREAM_MODE": "validated"
}
```

| 值 | 行为 |
| --- | --- |
| `validated` | 初始默认值；完整参数校验后输出，保持当前兼容性。 |
| `incremental` | 通过客户端协议资格检查的普通实时流，其原生工具参数逐段输出，完成时校验。 |

缺失或非法值回退 `validated`。该开关只影响工具参数的输出方式，不自动把 `stream: false` 改成流式，也不覆盖显式整段缓冲选择。

在 `src/core/config-manager.js` 定义默认值与校验。模式由入口方法显式传给 `_generateContentStreamRaw()`，生成器内部不读取该配置，否则非流式与整段缓冲会一起变成 incremental：`generateContent()` 与 `generateContentStreamBuffered()` 固定传 `validated`；普通实时流必须同时满足账号合并配置为 incremental、客户端协议受支持两个条件，才传 incremental，并在开始生成前冻结最终模式。

客户端协议由 `common.js` 中已确定的 `clientProtocol` 通过内部生成选项传给 adapter，不从用户请求体读取或允许请求体覆盖。adapter 根据该资格和账号合并配置确定最终模式；Claude、Chat Completions、Responses 以外的协议（包括 Gemini），以及缺少可信协议信息的内部直接调用，均强制使用 validated。账号配置不能绕过这一限制。

Gemini 流式转换丢弃工具参数增量是已有问题，本次不修复该转换逻辑，但必须隔离增量路径，保持其当前输出时机：即使账号配置为 incremental，Gemini 也不能在完整参数校验前收到工具开始事件。测试需同时覆盖合法与最终校验失败的参数。

本次不必同步增加后台 UI，先通过配置控制测试实例和灰度流量。

### 7. 补齐耗时指标

在同一请求标识下区分请求与上游尝试，采用单调时钟计算耗时，跨层比较时使用一致的请求时间原点。现有上游尝试追踪与下游发送日志通过请求标识、尝试序号关联；上游流结束不等于下游发送结束，不能提前把两者都记为完成。

| 指标 | 记录位置与意义 |
| --- | --- |
| 上游响应头 | 传输层收到响应头，区分内容开始前的等待。 |
| 上游首段思考、正文、非空工具参数 | `streamApiReal()` / 追踪层分类记录真实内容到达；工具名称或空参数开始不计入首段参数。 |
| 下游首段思考、正文、非空工具参数 | 写入被接受时记录，覆盖 Claude、Chat Completions、Responses 的对应事件。 |
| 单个工具调用 | 通过请求 ID、尝试序号和稳定内部 `callKey` 关联首段非空参数到达、身份就绪、首次参数写入、完整校验完成及暂存原因。 |
| 工具参数完成 | 按同一 `callKey` 记录完整参数校验完成时间，并关联该调用的首段参数时间。 |
| 参数快照 | 非空字符串片段之后又收到非空完整对象的次数，以及重新序列化结果与已累计字符串是否前缀一致；空对象占位单独计数且不纳入冲突分母；只记计数与布尔结果，不记参数内容。 |
| 请求及发送完成 | 分别记录上游完成、下游结束、事件数、字节数、缓冲模式与暂存原因。 |

首有效输出时间取实际非空思考、正文、工具参数中的最早值；首段正文和首段工具参数仍分别保留。响应头、心跳、空 start 事件不计入。服务端写入被接受不等于客户端已收到，客户端接收时间仍由外部探测独立测量。

请求级首段参数指标用于描述用户何时看到第一段参数。单个调用的本地转发等待则严格按相同的请求 ID、尝试序号、`callKey` 配对：该调用首段参数写入时间减去该调用首段非空参数到达时间。不能用工具 B 的上游首段时间减去工具 A 的下游首段时间，也不能跨重试尝试配对。

`callKey` 使用请求尝试内的本地序号等稳定标识，临时上游 ID 迁移时保持不变。原生工具、内容块索引、转换后的 tool index 或 Responses item 与它的对应关系仅在请求内部维护，不向标准 SSE 事件增加追踪字段，日志也不记录原始工具 ID 或参数。

前序工具阻塞、等待真实 ID、下游背压和参数完整校验缓冲分别标记。用于第二批开发门槛的 P90 优先使用受支持协议下首段参数到达时身份已就绪、无前序工具阻塞且无背压的首个原生调用，以其配对等待评估参数缓冲收益。存在其他等待原因的调用单独分组，不混入这一 P90；原因不明、配对缺失或仅有空对象参数的样本不纳入。各原因可能重叠，不能把原因时长简单相加后从总等待中相减；同时报告符合条件的样本数与覆盖比例，样本不足时先补采集。

日志沿用现有 opt-in 追踪和脱敏原则，只记录时间、分类、计数、实际模型、有效 effort、模式及脱敏路由标识，不记录密钥、提示词、图片或工具参数。新增追踪应有大小上限，避免逐片段输出大日志。

## effort 与上游等待的后续处理

`src/providers/claude/kiro-effort.js` 的思考与 effort 映射已在 2026-11-04 按 Kiro 模型 schema 调整，并补充了回归测试：可开关思考的模型发送原生 `thinking.type`，auto 模式对有原生思考的模型停用兼容 XML，不支持的档位降到最近的较低档位，详见 [Kiro 提示词策略与验收](KIRO_PROMPT_POLICY.md)。本方案不再改动该映射；未指定 effort 时仍不静默降为 low，不给不支持的模型加入额外字段。

低 effort 在本次短文探测中更早输出正文，但不代表编程质量已经验证。轻量入口可以明确选择低 effort；编程入口继续尊重调用方选择，不自动从提示词猜测任务复杂度。

分段指标上线后，再固定模型、effort、上下文规模、账号和出口代理进行上游等待对照。若比较直连、Rust sidecar 或 Go TLS sidecar，必须显式固定同一出口代理；当前代理解析随路径不同可能变化，单纯关闭 sidecar 不能构成有效对照。本机 Kiro IDE 的 Opus 5.5 请求走 CreateResponse（`runtime.us-east-1.kiro.dev`），本项目走旧端点；以 IDE 的使用体验作参照时，端点本身也是变量，对照中需注明。本方案不以更换端点作为优化手段。

如确需进一步拆分网络耗时，再在传输层补充请求体读取、连接、上游响应头和首字节阶段计时。当前没有足够证据将重写传输层排在工具输出改造之前。

## 测试与验收

### 必须证明的行为

| 场景 | 验收断言 |
| --- | --- |
| 首段提前发送 | 上游仅推入第一段参数，连接保持打开且不发送 stop；下游已经读到非空参数增量。不能只断言最终 JSON。 |
| 多段拼接 | 所有增量拼接后与预期参数一致，每段只发送一次；同一工具 ID、名称与块索引稳定。 |
| 完整对象替换 | 非空对象在未发送时允许替换；已发送兼容前缀只补后缀；冲突明确失败；validated 保持现有行为。 |
| 空对象占位 | 先收到 `'{"path":"x"}'` 再收到 `input:{},stop:true`，两种模式最终参数都为 `{"path":"x"}`，不生成替换更新、不计入快照冲突；真正无参数且明确结束的调用仍输出 `{}`。 |
| ID 与交错 | 真实 ID 晚到、缺失 ID、含糊片段、A/B 交错、正文/思考切换均无串参、重叠块或死锁；正文与已打开工具块的相对顺序按 validated、incremental 分别断言。 |
| 文本工具去重 | 原生先到、文本先到、两个独立原生 ID 参数相同均保持约定。 |
| 完整性与预算 | 无参数对象、错误 JSON、截断帧、EOF、参数上限、调用数上限、队列上限、中文和跨片段代理对均有明确结果。 |
| 错误与资源释放 | 部分参数发出后不重放、不伪造成功；取消、断连和写超时终止上游并释放队列、迭代器、计时器和插槽。 |
| 错误恢复提示 | 对未输出、已输出部分参数、仅内部消费事件和写入状态未知分别断言；已输出片段的失败调用不能附带“未输出工具调用”的提示，也不能暗示此前所有工具均未完成。 |
| 重试范围 | 尚未写出任何模型事件时，按现有错误分类和预算重试或切换账号；已写出思考、正文或工具事件后不再重放，即使首段工具参数尚未发出，也不能重试。 |
| 入口模式 | 配置为 incremental 时，`generateContent()` 与显式整段缓冲仍按 validated 输出，结果与当前版本一致。 |
| 协议资格隔离 | 配置为 incremental 时，Gemini、其他未支持协议和缺少可信协议信息的内部调用仍强制 validated；合法工具维持原输出时机，参数最终校验失败时不得提前输出工具开始事件；请求体不能伪造资格绕过限制。 |
| 协议与计量 | Claude、Chat Completions、Responses 的增量与终止事件正确；非流式、显式缓冲、usage 和缓存提交保持一致。 |
| 首字口径 | 响应头、心跳、空事件与占位工具不能计入真实首字，服务端接受写入与客户端接收分别统计。 |
| 工具耗时配对 | A 先声明、B 先收到参数、A 先输出时，分别用各自 callKey 配对，不能跨工具或尝试相减；ID 迁移保持关联，前序阻塞、等待 ID、背压和缺失配对的样本不混入开发门槛 P90。 |

## 实施与上线顺序

1. **第一批：分段计时。** 先补齐真实内容分类及请求/尝试/callKey 关联，保持现有输出方式，取得当前版本基线。同时统计非空参数快照的前缀一致比例与空对象占位次数，并在测试实例上增加大参数工具探测（例如写长文件的参数，只生成不执行），用单次串行请求进行，避免影响线上会话。基线在 2026-11-04 的思考与 effort 调整部署后采集，或在记录中注明服务版本，避免首段思考时间的变化混入工具输出对比。直连旧端点的探测使用 Python 或项目的 axios 路径：2026-11-04 用 Node 内置 `fetch` 发送同一请求体返回 `INVALID_MODEL_ID`，改用 Python 后立即成功，原因未查明；经测试实例发出的探测走项目自身的 axios 请求，不经过 Node 内置 `fetch`。
2. **第二批：工具增量输出。** 进入条件：第一批获得足够的同一调用配对样本，在受支持协议、首段参数到达时身份已就绪、无前序工具阻塞和无背压的首个原生调用分组中，参数缓冲等待达到用户可感知的量级（拟定 P90 不低于 1 秒，可按第一批数据调整），且非空参数快照冲突罕见。报告样本数与覆盖比例，不用请求级跨调用时间差或空对象占位计数判断门槛。样本不足时补采集，不满足收益或兼容条件时停在第一批，只保留计时。满足后完成状态机、调度、协议资格隔离、错误提示、兼容边界和回归测试；默认仍为 validated，在测试实例开启 incremental。
3. **第三批：小范围灰度。** 先让测试实例走与线上一致的 CLIProxyAPI 链路，确认参数片段逐段到达客户端；若中间层整段缓冲工具参数，先处理中间层，不扩大灰度。固定可比请求条件，对照首段参数、本地转发等待、错误率（含首段参数发出后的失败次数）、内存、背压和请求总用时；确认客户端能处理参数片段。
4. **第四批：上游等待优化。** 根据分段数据决定是否需要传输层计时或代理/sidecar 对照，再独立评估轻量请求的 effort 策略。

第一阶段核心验收标准：上游尚未完成参数生成时，经 CLIProxyAPI 后的客户端已经收到真实参数片段；最终参数准确，异常明确终止，现有 validated、非流式和显式整段缓冲行为可用。

若灰度出现快照冲突、客户端兼容问题、重复工具、异常完成或内存增长，将 `KIRO_TOOL_STREAM_MODE` 切回 `validated`，按实际配置加载方式重载或重启，并确认新请求恢复旧路径。已发出片段的在途请求不能追溯回滚，应按对应模式完成或明确失败。分段计时可继续保留以支持定位。

不以提前输出空 start、伪造正文、减少校验或静默降低 effort 作为验收通过条件。请求总用时是否下降单独报告；没有可比证据时不承诺固定秒数或倍数收益。
