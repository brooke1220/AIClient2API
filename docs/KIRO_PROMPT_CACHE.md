# Kiro 缓存读写计量

本功能为缺少缓存明细的 Kiro 响应补充**本地估算**。上游明确返回的非缓存输入、缓存读取、缓存写入和输出始终优先，包括明确的 `0`。它不会创建本地回答缓存，也不能证明上游缓存实际命中或 credit 实际减少。

## 开启方式

在后台进入 **配置管理 → Kiro 缓存计量**，可修改模式、策略、默认有效期、账本上限和各模型最小缓存长度。点击页面的“保存配置”后会自动重新加载配置，后续请求使用新设置；账号池节点单独设置的同名配置优先。

默认有效期在界面中以秒填写，支持三位小数（例如 `1.001` 秒），保存时换算为整数毫秒。模型门槛可逐行添加、编辑或删除，删除全部覆盖并保存会恢复模型默认规则。无效模式、超范围数字、空或重复模型 ID、非正整数门槛会阻止保存；服务端也执行校验。

也可以在 `configs/config.json` 添加以下配置，或在对应 Kiro 账号池节点覆盖；文件修改后需重新加载配置或重启服务：

```json
{
  "KIRO_PROMPT_CACHE_MODE": "observe",
  "KIRO_PROMPT_CACHE_POLICY": "auto",
  "KIRO_PROMPT_CACHE_DEFAULT_TTL_MS": 300000,
  "KIRO_PROMPT_CACHE_MAX_ENTRIES": 65536,
  "KIRO_PROMPT_CACHE_MIN_TOKENS_BY_MODEL": {}
}
```

| 配置 | 行为 |
| --- | --- |
| `KIRO_PROMPT_CACHE_MODE=off` | 默认值；保留已有返回行为，不建立本地前缀账本。上游缓存明细仍正常透传。非法模式按 `off` 处理。 |
| `KIRO_PROMPT_CACHE_MODE=observe` | 建立本地账本，在 `[Kiro Usage]` 日志的 `cacheAccounting.observed` 中记录假设拆分，不将估算写入客户端缓存字段。此模式无需另开请求追踪。 |
| `KIRO_PROMPT_CACHE_MODE=estimate` | 将缺失的缓存字段按账本估算补全；统计页显示估算或混合来源。 |
| `KIRO_PROMPT_CACHE_POLICY=auto` | 请求带缓存声明时采用 `explicit`，否则采用 `history`。非法策略回退 `auto`。 |
| `KIRO_PROMPT_CACHE_POLICY=explicit` | 只处理工具、system、消息内容块的 `cache_control` 及顶层自动缓存声明。没有声明时不主动推断历史命中。 |
| `KIRO_PROMPT_CACHE_POLICY=history` | 估算工具、system 和历史消息形成的稳定前缀；本轮用户消息不主动纳入缓存覆盖范围。 |
| `KIRO_PROMPT_CACHE_DEFAULT_TTL_MS` | 未声明 TTL 时使用，默认 300000 毫秒；接受正安全整数，最多 3600000 毫秒，无效值回退默认。显式 `ttl: "5m"` / `"1h"` 优先。 |
| `KIRO_PROMPT_CACHE_MAX_ENTRIES` | 进程内账本条目上限，默认 65536，最多 1048576。不是提示词长度限制。多节点使用同一进程账本，配置较小上限的节点提交时会触发相应淘汰。 |
| `KIRO_PROMPT_CACHE_MIN_TOKENS_BY_MODEL` | 按**最终上游模型 ID**覆盖可缓存前缀的本地最小 token 数，值须为正安全整数。默认 Sonnet 家族为 1024，其它模型为 4096；这些是估算器规则，不代表已验证的 Kiro 服务端门槛。 |

建议先用 `observe` 对照同一会话重复请求的日志，确认模型、账号和会话稳定后，再将模式改为 `estimate`。无需修改客户端即可使用 `history`；Claude 缓存声明适合使用 `explicit`。可用明确的 `metadata.session_id` 区分共享 API Key 下的独立会话。

## 计量规则

1. 指纹来自最终发送给上游的工具和消息：包含工具说明转换、图片规范化、历史裁剪、实际模型、端点及思考设置。声明本身不作为提示词文本参与指纹。账本只保留哈希与 token/TTL 等数字元数据，不保留提示词、图片或凭证原文。
2. 账本按客户端会话、上游账号、端点、模型和对话隔离。前缀发生变化时，其后各段都失效；上游 access token 正常轮换不会单独导致缓存失效。身份无法稳定匹配时可能出现保守的未命中。
3. `explicit` 支持最多四个声明和 5 分钟/1 小时 TTL；长 TTL 的断点必须排在短 TTL 之前。每个断点最多向前寻找 20 个内容位置，工具调用/结果组按组计位置。顶层自动声明指向最后一个实际内容块，已有相同终点的显式声明优先。
4. 断点所在内容被裁剪、内联或变换后无法可靠定位时，整个显式方案停止估算，记录 `unmapped_breakpoint`。非法声明、断点过多或 TTL 顺序非法同样不会退回更宽的历史估算。
5. 在每次实际发起上游请求时冻结本次命中结果，只能读取已经提交的条目。两个同时发起的冷请求不会因为其中一个后来完成而相互追认命中。成功且通过完整性检查后才写入或续期；失败重试、取消、损坏流、缓冲超限不会提交。
6. TTL 从该次上游请求发起时间计算。响应耗时超过 TTL 时不补建已过期条目；较早发起、较晚完成的请求不会缩短更新条目的有效期。
7. 按最终总输入与可缓存前缀的估算比例拆分，采用整数并保持总数守恒。总输入沿用现有上游 usage、上下文占比或本地 token 估算来源。图片沿用本项目的单图近似值，不能据此验证精确 token 数。
8. 上游已提供的字段逐项保留。如果上游同时给出总输入和三个输入分项中的两个，且已知分项之和不超过总量，则用差值补齐唯一缺失分项；该结果按上游来源记录，适用于 `off`、`observe`、`estimate`，不会推断缓存写入 TTL。不能唯一确定分项时，仅在 `estimate` 中按本地比例补充。已知非缓存输入和缓存计数不因本地估算而被改写；本地估算总量也不会强制补成缓存写入。冲突时保留原生字段，不生成负数，不反推或伪造 credit 数据。

## 协议与统计口径

Claude / Anthropic 最终用量满足：

```text
总输入 = input_tokens + cache_read_input_tokens + cache_creation_input_tokens
```

OpenAI Chat 的 `prompt_tokens`、Responses 的 `input_tokens` 和模型统计页的“输入 Token（含缓存）”表示上述总输入。`cached_tokens` 是其中的缓存读取子集，不能重复加到输入总数。估算写入同时提供标准 `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` 分项，两项相加等于缓存写入。

`estimate` 模式的普通实时流在 `message_start` 使用输入/缓存零占位，`message_delta.usage` 给出最终一致快照。`KIRO_CC_BUFFERED=true` 的缓冲流在完整接收且通过检查后，回填起始事件的最终输入和缓存计数；首字会等待上游完成。非流式响应使用同一最终结果。统计和 Potluck Key 用量统一消费最终快照，可以覆盖较大的起始估算，避免逐字段取最大值造成重复累计。

统计页新增“缓存读取”“缓存写入”和来源请求数，Provider 卡片与模型表使用相同口径。来源分为上游、估算、混合、未标注；混合表示读取与写入分别来自原生和估算字段。来源标记只在内部统计和日志保留，不向协议 `usage` 添加非标准来源字段。OpenAI 的缓存写入没有独立标准字段，内部统计仍保留原生结果中的写入计数。

统计文件升级到 `schemaVersion: 2`，保留原来的累计输入、输出和读取数据，新增 `cacheCreationTokens`、四类来源请求数及 `cacheStatsStartedAt`。历史请求归入未标注，历史写入字段初始化为 `0`，页面会解释其含义；不将这些零值视为已确认的历史无写入，也不回算旧输入口径。仅清空 Token 时保留请求次数，原请求来源归入未标注，并重新记录来源统计开始时间。

## 当前边界与验证

账本为进程内存，重启后冷启动；多个进程或实例之间不共享命中记录，观察/估算模式之间切换可复用同一进程内有效记录。此次没有引入 Redis 或磁盘持久化，没有依据 credit 变化猜测缓存命中，也没有承诺减少真实上游费用。

新增自动测试覆盖 TTL、断点移动、声明校验、图片指纹、账号/会话隔离、并发、失败/取消、普通流/缓冲流/非流式、跨协议总数守恒、统计迁移/落库/重置和最终快照替换。请求流程测试使用本地模拟 AWS 事件帧，没有调用真实 Kiro 账号，真实服务端缓存行为仍需观察模式验证。
